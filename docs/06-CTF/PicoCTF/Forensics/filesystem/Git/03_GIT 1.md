# 🕵️ Category: Forensics / Git

---

## 📘 Description

The challenge provides a disk image and asks:

> **Can you find the flag in this disk image?**

The investigation revealed that the disk contains a Linux filesystem with a Git repository located at:

```text
/home/ctf-player/Code/secrets/.git
```

The current Git commit indicates that the flag was removed, suggesting that the deleted file could still be recovered from the Git history.

---

## 🛠 Tools Used

- `gunzip`
    
- `file`
    
- `mmls`
    
- `fsstat`
    
- `fls`
    
- `icat`
    
- Python 3
    
- Script genérico para análisis de objetos Git
    

---

## ⚙️ Methodology

### 1. Descompresión de la imagen

El archivo proporcionado tenía extensión `.gz`, por lo que primero se descomprimió:

```bash
gunzip disk.img.gz
```

![[03_descomprimir_disco.png]]

Se verificó el tipo de archivo:

```bash
file disk.img
```

La salida indicó que se trataba de una imagen de disco con una tabla de particiones MBR:

![[03_Informacion_disco.png]]

---

### 2. Análisis de la tabla de particiones

Se utilizó `mmls` para identificar los offsets de las particiones:

```bash
mmls disk.img
```

El resultado fue:

![[03_metadotos_particion1.png]]

Se identificaron tres particiones:

|Partición|Offset|Tipo|
|---|--:|---|
|1|`2048`|Linux / Ext4|
|2|`616448`|Linux Swap|
|3|`1140736`|Linux / Ext4|

La partición 2 corresponde a memoria `swap`, por lo que no fue priorizada.

---

### 3. Identificación del sistema de archivos

Se analizaron las particiones Linux mediante `fsstat`.

Para la primera partición:

```bash
sudo fsstat -o 2048 disk.img
```

Se obtuvo:

![[Pasted image 20260828201337.png]]

Posteriormente se analizó la tercera partición:

```bash
sudo fsstat -o 1140736 disk.img
```

El resultado indicó:

![[03_metadatos_particion3.png]]

Esto permitió determinar que la partición ubicada en el sector `1140736` correspondía al sistema de archivos raíz de la máquina.

A partir de este punto se utilizó el siguiente offset:

```text
1140736
```

---

### 4. Exploración del sistema de archivos

Se listó el directorio raíz:

```bash
fls -o 1140736 disk.img
```

Entre los directorios encontrados estaba:

![[03_directorios_particion3.png]]

El directorio `/home` tenía el inodo:

```text
64770
```

Por ello se realizó una exploración recursiva:

```bash
fls -o 1140736 -r disk.img 64770
```

La estructura relevante encontrada fue:

```text
/home
└── ctf-player
    └── Code
        └── secrets
            └── .git
```

![[03_Home_subcarpetas.png]]

Esto confirmó la existencia de un repositorio Git en:

```text
/home/ctf-player/Code/secrets/.git
```

---

### 5. Análisis del repositorio Git

Dentro del directorio `.git` se encontraron los elementos habituales de un repositorio:

```text
branches
hooks
info
refs
objects
HEAD
config
index
COMMIT_EDITMSG
logs
```

También se identificaron objetos Git almacenados en `.git/objects`.

La referencia:

```text
.git/refs/heads/master
```

correspondía al inodo:

```text
65711
```

Se recuperó mediante:

```bash
icat -o 1140736 disk.img 65711
```

El resultado fue:

![[03_inode_rama_master.png]]

```text
5fb8194539c770a830b8ba089a50778c07072b03
```

Este hash corresponde al commit actualmente referenciado por `master`.

---

### 6. Análisis del commit actual

El objeto correspondiente al commit se encontraba en:

```text
.git/objects/5f/b8194539c770a830b8ba089a50778c07072b03
```

Su inodo era:

```text
65709
```

Se recuperó con:

```bash
icat -o 1140736 disk.img 65709 > commit.obj
```

Para interpretar el objeto Git se utilizó un script genérico basado en Python y `zlib`.

El script permite identificar automáticamente si un objeto Git corresponde a:

- `commit`
    
- `tree`
    
- `blob`
    
- `tag`
    

Ejemplo de uso:

```bash
python3 git_object.py commit.obj
```

La salida  fue:

![[03_visualizar_ultimo_commit.png]]

El mensaje del commit:

```text
Remove flag
```

constituyó una pista fundamental.

El commit actual había eliminado la flag, pero conservaba como padre el commit:

```text
177789af0b300e043ea8f54ea57d6cee352291ae
```

---

### 7. Recuperación del commit anterior

El commit padre se encontraba en:

```text
.git/objects/17/7789af0b300e043ea8f54ea57d6cee352291ae
```

Su inodo era:

```text
65700
```

Se recuperó mediante:

```bash
icat -o 1140736 disk.img 65700 > parent.obj
```


Posteriormente se utilizó nuevamente el script genérico:

```bash
python3 git_object.py parent.obj
```

El resultado fue:

![[03_visualizar_penultimo_commit.png]]

Este commit tenía como mensaje:

```text
Add flag
```

Por lo tanto, se determinó que la flag había sido agregada en este commit y eliminada posteriormente.

---

### 8. Análisis del objeto Tree

El commit `Add flag` apuntaba al árbol:

```text
a62340e078686778969b9a555fc722147cf14e5a
```

Este objeto estaba almacenado como:

```text
.git/objects/a6/2340e078686778969b9a555fc722147cf14e5a
```

y correspondía al inodo:

```text
65698
```

Se recuperó mediante:

```bash
icat -o 1140736 disk.img 65698 > tree.obj
```

Luego se analizó con el script genérico:

```bash
python3 git_object.py tree.obj
```

La salida mostró:

![[03_inspeccionar_arbol.png]]

Esto permitió identificar el archivo eliminado:

```text
flag.txt
```

y su objeto Git asociado:

```text
f150f47a5dabfb4397706aa18905df936595a86e
```

---

### 9. Recuperación del blob de `flag.txt`

El objeto correspondiente al archivo estaba almacenado en:

```text
.git/objects/f1/50f47a5dabfb4397706aa18905df936595a86e
```

Su inodo era:

```text
65695
```

Se recuperó de la imagen:

```bash
icat -o 1140736 disk.img 65695 > flag.obj
```

Al intentar visualizarlo directamente con `icat`, se observaron caracteres ilegibles. Esto ocurre porque los objetos Git se almacenan comprimidos mediante `zlib`.

En lugar de crear otro script específico, se utilizó el mismo script genérico:

```bash
python3 git_object.py flag.obj
```

El script identifica automáticamente el encabezado Git:

```text
blob <tamaño>
```

y posteriormente muestra el contenido del objeto.

El objeto fue identificado como un `blob` (_Binary Large Object_) es el tipo de objeto dedicado exclusivamente a guardar el contenido puro de un archivo (datos o texto), correspondiente al contenido original de `flag.txt`.

![[03_visualizar_blob.png]]

## 🔗 Git Object Chain

La relación entre los objetos recuperados puede representarse de la siguiente manera:

```text
master
  │
  ▼
5fb8194539c770a830b8ba089a50778c07072b03
  │
  │ "Remove flag"
  │
  ▼
177789af0b300e043ea8f54ea57d6cee352291ae
  │
  │ "Add flag"
  │
  ▼
a62340e078686778969b9a555fc722147cf14e5a
  │
  │ tree
  ▼
f150f47a5dabfb4397706aa18905df936595a86e
  │
  │ blob
  ▼
flag.txt
  │
  ▼
FLAG
```

La flag pudo recuperarse porque Git mantiene los objetos de commits anteriores aunque el archivo ya no exista en el estado actual del repositorio.

---

## 🧠 Key Finding

El punto fundamental de la resolución fue reconocer que el commit actual tenía como mensaje:

```text
Remove flag
```

En lugar de buscar únicamente archivos existentes en el sistema de archivos, se analizó el historial Git.

El commit anterior:

```text
Add flag
```

contenía un árbol que todavía referenciaba:

```text
flag.txt
```

El contenido de este archivo permanecía almacenado como un objeto `blob`, permitiendo su recuperación forense incluso después de haber sido eliminado del último commit.
